# ETT 油温予測 PoC — 変圧器の予防保全に向けた先読みの技術検証

電力用変圧器の油温（OT）を数時間先まで予測し、「高温になる前に知らせる」ことがどの程度できるかを、公開ベンチマーク ETT で検証した PoC です。
クライアント向けの報告スライドは `reports/slides/ett_oil_temperature_poc.pdf`（生成元 pptx も同梱。`scripts/build_slides.js` で再生成、文章は `docs/slides_text.md`）。

## 結論（テスト期間 2017-11 〜 2018-06、起点までの観測だけを使う条件 B）

| 設備 | 6h 先の MAE | 比較したベースライン中で最良のものとの比 | 持続予測比 | 高温の事前検知（学習期間の上位 5% 点を閾値に固定） |
|---|---|---|---|---|
| ETTh2 | **1.95 ℃** | −18%（リッジ 2.37） | −56%（4.44） | 連続超過区間 13 のうち 10 で事前の的中予測あり（77%）。通知は期間全体で 12 件、うち誤通知 3 件。検知できた区間の最初の的中予測は平均 4.0 時間前 |
| ETTh1 | 1.11 ℃ | −4%（持続 1.15） | −4% | テスト期間に閾値超えなし（上位 10% 点でも 0）→ 評価保留 |

- **改善の大きさは設備で違う。** ETTh2 の 6h 改善は対象月ごとに見ても 8 か月すべてで持続比 28〜64%、リッジ比 3〜28%、週単位では 97% の週で持続に、91% の週でリッジに勝つ。ETTh1 は月によって負ける（週単位で 54%）ので、3.7% の改善は安定した効果とは言えない。
- **1h 先**: ETTh1 は持続 0.44 → 0.42 ℃で差が小さい。ETTh2 は持続 0.91 → 0.37 ℃（−59%）で、1h でもモデルの価値がある。
- **24h 先**: 持続予測に対する明確な改善は確認できなかった（ETTh1 1.63 → 1.80 で悪化、ETTh2 3.19 → 3.17）。
- **効いている情報**: 油温の履歴に**カレンダー（対象時刻の時刻・季節）**を足す効果が大きい。負荷の追加効果は設備・期間で一貫しない（6h・テスト: ETTh1 は −1〜2%、ETTh2 は +7% 悪化。ETTh2 は負荷なし 1.83 ℃ が最良）。主結果 1.95 ℃は**事前に固定した全特徴量（条件 B）**の値で、検証で最良の特徴量構成を選んだものではない。「対象時刻の負荷が既知」という条件 A でも改善は小さい。
- 時点単位で見ると、高温状態そのものを継続して当てられた割合は 42%（65 時点中 27）。区間を一度捉えることと、高温を継続して当てることは別。
- 高温区間 13 件は 2018 年 5〜6 月に集中し、同日の再超過も含む。予測できるのは油温と「相対的高温」の代理指標まで。故障・点検・介入の記録が無いので、保全効果そのものは今回は評価できない。未学習の設備への汎化も示していない。

## 課題の設定と仮定

- **記法**: 起点 s = 予測を行う時刻、対象 T = s + h。目的変数は OT[T]。
- **2 つの評価条件**: 条件 B = 起点 s までの観測だけ（運用条件）。条件 A = B ＋ 対象時刻 T の負荷 6 種（課題ルール「t=T の油温を予測する際には t=T での特徴量を使用してよい」の解釈。将来の負荷が運転計画で既知という条件付き）。
- **分割（暦で固定）**: 学習 2016-07-01〜2017-06-30、検証 2017-07-01〜2017-10-31、テスト 2017-11-01〜2018-06-26。学習に使う行は対象時刻 T が学習終了前のもの（ラベルが検証期間に食い込まない）。検証・テストの評価行は対象時刻 T と起点 s の両方がその期間に入るもの（各境界の先頭 h 時間は、その起点ではモデルを確定できないので除外）。ハイパーパラメータ・早期終了・残差／直接の選択は検証期間だけで行ったが、EDA は全期間で行っているのでテストを「完全に未見」とは言わない。
- **主ホライズン 6h**（数時間前の確認・運転調整を想定）。1h・24h は補助。ホライズンごとに直接予測。
- **高温の代理指標**: 学習期間の OT 上位 5% 点（h1 35.2 ℃、h2 46.4 ℃）を固定。設備の危険温度ではない。上位 10% 点も併記。
- **警報の 2 種類**: 「高温状態の予測」（対象時刻に閾値超えかを当てる。時点単位の再現率・適合率）と「高温になる前の検知（onset）」（起点では閾値以下、対象で超え）。連続した超過は 1 区間、連続した警報は 1 通知に集約する。1 通知が複数の区間に対応することがある。誤通知 = 通知区間の対象時刻が一度も閾値を超えなかった通知。先行時間 = 検知できた区間の最初の的中予測の起点から実際の超過時刻まで（通知の開始時刻からではない）。定義は `tests/test_evaluate.py` の人工系列で固定している。
- 設備ごとに別モデル。運用時も OT は毎時観測できる前提（欠測時の代替推定は対象外）。到着遅延 0、再学習なし。
- 事前に置いた成功条件: 6h・条件 B で最強ベースラインより MAE 10% 以上改善、通知 1 件/日以下で onset 再現率 50% 以上 → ETTh2 は満たす、ETTh1 は精度改善が小さく警報は評価不能。

## 手法

- ベースライン: B0 持続予測 OT[s]、B1 季節ナイーブ OT[T−24h]、B2 リッジ回帰。
- 本命: LightGBM（L1 目的関数、検証期間で早期終了）。目的変数は残差 OT[T]−OT[s]（検証で直接予測より良かった）。特徴量は OT の履歴（現在値・代表ラグ・差分・移動統計）、対象時刻の周期特徴、負荷の現在値・差分・24h 平均、（条件 A のみ）対象時刻の負荷。
- リーク防止: 条件 B の特徴量は起点 s を含む過去方向の値だけ（OT[s] は観測済みなので使える）。末尾を切っても値が変わらないことを `features.check_no_leakage` で確認。スケーラーは学習期間で fit。
- アブレーション（6h・診断目的）: OT 履歴のみ → ＋カレンダー → ＋起点までの負荷 → ＋対象時刻の負荷。最良構成の選択には使っていない。
- 安定性（`scripts/run_stability.py`）: テスト期間を対象時刻の月・週で切り、持続・リッジ・LightGBM を同じ行で比較。

## 再現手順

```bash
uv sync
uv run python scripts/run_eda.py        # reports/figures/eda_*.png, reports/eda_summary.md
uv run python scripts/run_baselines.py  # reports/results_baselines.md
uv run python scripts/run_lgbm.py       # reports/results_lgbm.md（約 1.5 分）
uv run python scripts/run_stability.py  # reports/results_stability.md
uv run python scripts/make_figures.py   # reports/figures/res_*.png
uv run pytest -q tests                  # 警報指標・分割の単体テスト
```

Python 3.12 / pandas / scikit-learn / LightGBM 4.7。乱数シードは固定。

## 限界と次のステップ

- 24h 先は今回の特徴量では明確な改善が得られなかった。外気温・気象予報の追加が最有力の候補（未検証）。
- 2 台で良好でも未学習の設備への汎化は示していない。設備ごとの再学習と、ドリフトの監視が要る。
- 高温イベントが少ない期間（h1 のテスト期間）では警報性能を評価できない。長期のデータか、複数設備の横断評価が要る。
- 現場実証に進む条件: 対象設備の OT と負荷が毎時取れること、閾値の業務上の意味（危険温度・運転上限）の確定、警報を受けて誰が何をするかの運用設計。
